# PRD：Zotero 到证据包的无人值守自动化

## 1. 摘要

本需求定义水利科研知识平台第一条必须真正运行的自动化链路：团队成员把论文加入指定 Zotero 共享库后，指定制卡机在无人打开 Codex 窗口、无人发起对话的情况下，自动检测论文、取得并校验 PDF 全文、为尚无证据卡的新论文生成唯一证据包，并将可共享结果同步到 GitHub。已有非占位证据卡不自动重新生成。

2026-09-08 决策更新：默认改为单 Agent、模板驱动的详细粗卡；六角色强制要求已撤销。当前禁止自动推送 GitHub，须用户明确授权。本文的无人值守目标不是现有功能清单，实施现状见第 8 节。

本阶段只做到证据包。候选主题、正式主题和科研 idea 不在本阶段实现。

## 2. 联系人与角色

| 角色 | 当前职责 | 备注 |
|---|---|---|
| 导师 | 确认证据卡模板与科研质量，查看进度和阻塞 | 具体人员信息待录入 |
| 学生 | 使用私人 Zotero 账号向共享库新增论文或补充 PDF | 不直接维护个人证据卡目录 |
| 产品负责人 | 维护范围、假设和验收标准 | 具体人员待指定 |
| 自动化维护者 | 实现、部署和修复后台流程 | 具体人员待指定 |
| SYS-CARD-01 | 无人值守检测、制卡、写入和同步 | 唯一自动化写入身份 |

## 3. 背景

团队已经形成候选科研知识链路：信息入口、AI 初筛、Zotero 共享库、结构化证据卡、主题深化和科研 idea。但当前风险不是缺少更多概念，而是基础链路没有工程化：流程依赖个人电脑、个人操作记忆和对话上下文，无法无人值守运行，也无法在更换电脑后恢复。

原始讨论进一步表明：

- 每篇论文需要转化为结构化知识，而不是只生成摘要；
- 证据卡最终应支持主题形成，因此必须可追溯、可迁移和可比较；
- 证据卡模板非常关键，不能在未经小样本验证时批量处理数千篇论文；
- 证据卡模板由其他协作者以八个 Markdown 文件提供，不同论文类型使用不同模板；本自动化项目已经固定来源提交并完成版本化适配与静态校验，不复用来源脚本和工作流；
- 一个隔离 Agent 会话处理一篇论文，完成全文阅读、自动选型、详细填写和同会话自检；不增加固定子 Agent。
- 原始 PDF 不适合放入 Git，Zotero 继续作为文献与附件来源；
- 是否能在另一台电脑复现同一流程，是产品化的基本标准。

## 4. 目标

### 4.1 产品目标

让团队成员只需完成“向指定 Zotero 共享库加入论文或补充 PDF”这一动作，后续证据包处理无需人工启动。

### 4.2 第一阶段成功结果

- 新增带有可读取 PDF 的论文后，系统能够无人值守地产生唯一证据包；
- 先新增条目、后补充 PDF 时，系统能够等待并在 PDF 到位后继续；
- 系统重复运行、重启或重建本地状态时，不遗漏、不重复制卡；
- 流程失败时能够指出阻塞位置，不生成伪造的正式证据卡；
- 模型输出通过来源身份、阅读声明、归因格式、模板结构和写入保护后才能进入共享证据包；不声称机器已独立验证科研正确性。
- 新电脑能够依据 GitHub、Zotero 和重新提供的凭据恢复整个自动化流程。

### 4.3 最小验收指标

使用 2 篇正常 PDF 和 1 个缺失或不可读 PDF 的小样本验证：

1. 两篇正常论文各生成且只生成一个证据包；
2. 负面样本不生成正式卡，并形成明确阻塞状态；
3. 同一批数据连续运行两次，不新增重复证据包或重复事件；
4. 删除本地运行状态后重新对账，结果仍与 Zotero 和 GitHub 一致；
5. 整个过程不需要打开 Codex 对话窗口或人工点击“开始”。
6. 成功粗卡记录单会话 quality-audit.json，协议 rough-card-single-agent-v1、角色数 1、STRUCTURE_VALIDATED；区分原文陈述/转述、AI 推理与信息边界，不设人工核验任务。
7. 不设置逐卡人工复核或固定抽查条数作为运行前置。详细卡片能否改善最终主题、什么主题算达标仍待小样本验证；不得将结构通过写成科研质量已经验收。

机器格式检查不能证明科研正确性。人主要判断最终主题和 idea；本阶段不实现这两项，也不伪称成果等级已获保证。

## 5. 用户与使用场景

### 5.1 学生

场景：学生发现有价值的论文，将父条目和 PDF 加入团队 Zotero 共享库，或给已有父条目补充 PDF。

期望：不再手工创建目录、复制 PDF、发起 Codex 对话或判断是否重复生成。

### 5.2 导师

场景：导师希望知道文献处理是否持续推进、哪些已形成证据包、哪些因缺 PDF 或处理失败而阻塞。

期望：看到流程状态和可追溯结果，而不是学生排名或无意义的操作数量。

### 5.3 自动化维护者

场景：旧电脑损坏、程序升级或任务失败。

期望：可以依据仓库文档和安装脚本，在新电脑恢复流程并安全重跑。

## 6. 价值主张

- 学生只维护 Zotero，不重复维护个人证据卡目录；
- 导师看到可追溯的团队知识资产和真实阻塞；
- 一篇论文只有一个共享证据包，减少重复劳动；
- 自动化不依赖特定人的记忆、某次聊天或旧电脑状态；
- 后续更换证据卡模板、模型或主题方法时，已有来源和生成版本仍可追溯。

本阶段不声称证据卡一定能帮助学生快速进入研究方向，因为模板质量和主题效果尚未验证。

## 7. 方案

### 7.1 主流程

    定时或补跑触发
        → 检查 Zotero 是否可用并完成同步
        → 扫描指定共享库的父条目和附件变化
        → 与已有证据包和本地状态对账
        → 建立单篇论文任务
        → 定位并校验 Zotero 原始 PDF
        → 一个隔离 Agent 阅读完整 PDF、自动选型、模板详细填写与同会话自检
        → Python 校验来源记录、归因格式、模板结构和 manifest
        → 原子写入或更新证据包
        → 记录关键事件
        → 经用户明确授权后提交并推送 GitHub
        → 形成成功、等待或失败结果

### 7.2 状态边界

至少需要区分：

- 发现父条目；
- 等待 PDF；
- PDF 可读取；
- 等待生成；
- 正在生成；
- 生成成功；
- 生成失败；
- 质量失败；
- Git 同步失败；
- 需要人工处理。

状态名称和机器格式将在用户故事阶段确定。

### 7.3 证据包规则

- 以指定群组库中的 Zotero 父条目 Key 作为内部唯一标识；
- 目录采用 EV-父条目Key-简短标题；
- manifest 至少记录父条目 Key、PDF 附件 Key、PDF 哈希、创建与更新时间；
- 记录提示词版本、数据结构版本、各角色模型配置、处理程序版本和质量审计哈希；
- PDF 原文仍由 Zotero 保存，不复制到 GitHub；
- 主题只引用证据包，不复制证据卡；
- 同一论文面向不同主题的精读内容以后放入该证据包的 topic-readings 目录。

### 7.4 无人值守要求

- 运行时不得依赖 Codex 对话窗口；
- 检测、调度、失败重试和 Git 同步由后台程序执行；
- 团队级可调整路径和固定参数必须从单一总配置加载，不得散落在命令、脚本或源码中；
- 运行时状态、证据事实、密钥和程序协议不得伪装成用户配置；
- Python 后台程序是流程控制器，Codex 不能成为只有人发消息才运行的触发器；
- 当前阶段由 Python 后台程序非交互调用 Codex CLI，Codex CLI 使用制卡机上已登录的 Codex 订阅账号；
- 运行不依赖 Codex 对话窗口，但依赖 Codex CLI 已安装、账号登录有效且订阅额度可用；
- 单 Agent 编排与模型提供者分离；当前只实现 Codex CLI，更换提供者需要实现并测试适配器，不是任意填写模型工具名。
- 调用前检查 Codex CLI 与登录状态，登录失效、额度不可用或调用失败时进入明确阻塞，不伪造成功；
- 每篇论文独立会话，只在自己的临时工作区写中间文件，Python 写正式产物。

### 7.5 恢复与幂等

- Zotero 与 GitHub 是可恢复的数据源；
- 本地 .runtime 只是可重建缓存，不是唯一事实来源；
- 全量对账按父条目 Key 定位证据包，并按 card.md 是否仍为占位内容决定是否首次制卡；
- 当 card.md 已经是非占位卡时，无论任务被重复发现多少次都不再次调用 AI；
- 附件 Key 或 PDF 哈希变化只触发输入变化告警和人工处理，不自动覆盖旧卡；
- 恢复扫描不得把历史论文误记为恢复当天的新贡献；
- 自动化写入前先校验，成功后再更新状态；
- Git 推送失败不应导致重新生成第二份证据包。

### 7.6 人工参与边界

证据包生成前不设人工审核。以下情况需要人工处理，但不需要人工批准每篇论文：

- PDF 缺失；
- PDF 不可读取；
- Zotero 未同步或权限不足；
- AI 输出不满足机器校验并进入 `QUALITY_FAILED`；只有查明原因后才显式重试，不要求人工逐条修卡；
- Git 冲突或推送失败且自动重试无法恢复。

候选主题升级为正式主题仍需人工确认，但不属于本阶段。

### 7.7 已确认事实

- 所有老师和学生使用各自的 Zotero 私人账号；
- 只处理指定共享群组库；
- 共享库中的论文原则上都需要制卡；
- 必须取得 PDF 全文后才能制卡；
- 取消学生个人证据卡目录；
- 一篇论文一个共享证据包；
- 新论文的占位卡只自动生成一次粗证据卡，已有非占位卡不自动重新生成；
- 指定一台制卡机拥有写入权；
- 不追溯系统启用前的历史贡献；
- 人工新增论文、补 PDF 与系统制卡分别记录；
- 监控用于掌握进度和发现阻塞，不用于绩效评价；
- 系统每天需要形成“新增、完成、阻塞”摘要，但日报细节后置；
- 流程必须无人值守并可在新电脑恢复。
- 当前阶段使用制卡机上已登录的 Codex 订阅账号，由 Python 后台程序通过非交互 Codex CLI 发起制卡；不使用单独配置和计费的大模型 API。
- 论文类型由 Codex 自动判断并选择唯一启用模板，不设置“待人工确认类型”；置信度和理由只记录不阻塞，非法类型按生成失败处理。
- 模板升级不自动批量重制历史卡；类型纠正或明确重制时生成新版本并保留旧版本。
- 正式粗卡默认单 Agent、模板驱动；内容详细、来源与推理分开，不安排逐卡人工核验。
- 归因合约或工作流审计失败时不写正式卡，任务进入 `QUALITY_FAILED`，日常运行不自动反复消耗模型额度。
- 已有正式卡只能通过不覆盖的试运行评估新流程；自动重制和版本迁移另行设计。

### 7.8 待验证假设

- Zotero 本地接口和文件同步能够稳定提供指定群组库的父条目、附件和 PDF；
- 能够可靠取得新增者或附件补充者身份；
- 父条目 Key 在指定群组库范围内足以长期定位证据包；
- 单一制卡机能够避免 Git 写入冲突并满足近期处理量；
- Codex CLI 能在无人打开窗口时稳定完成单篇详细制卡；实际耗时和下游主题收益尚待验证。
- 团队拥有将目标论文 PDF 交给 Codex 服务处理的权限，并接受其数据处理和保留政策；
- Codex 订阅账号的登录状态可以在指定制卡机上维持，偶发失效时能够被检测并经人工重新登录后恢复；
- 不做 OCR 的第一版可以覆盖首轮样本；
- 外部提供的多类型证据卡模板经灾害链小样本验证后能够支持主题形成；
- Codex 能够在无需人工确认类型的情况下选择唯一启用模板，且记录的分类理由足以追溯明显误判；
- 单 Agent 能降低重复上下文开销，但没有独立语义复核，归因正确性和重要内容完整性仍有风险。

### 7.9 当前非目标

- RSS 和期刊推送；
- Zotero 入库前价值判断；
- OCR；
- 与当前归因适配无关的大规模模板重写；
- 候选主题和正式主题生成；
- 科研 idea；
- 实验执行、论文写作或基金全文生成；
- 学生排行榜、积分和绩效考核；
- 微信或邮件通知；
- 多台制卡机并行写入。

## 8. 发布与实施顺序

### 阶段 A：自动化骨架

确定后台执行方式、配置边界、任务状态、幂等标识和恢复命令。完成 Zotero 只读探测，不生成证据卡。

### 阶段 B：检测与 PDF 门禁

实现父条目检测、PDF 附件识别、全文可读性检查、等待 PDF 和失败状态。使用小样本验证。

### 阶段 C：证据包写入

实现目录命名、manifest、占位卡、原子写入和重复运行保护。占位 card.md 只写“待生成证据卡”和 `PLACEHOLDER` 状态，不预设正式证据字段；所有来源与输入元数据放在 manifest.json。占位卡不得被当作正式科研证据，重复运行不得覆盖已经填写的卡片。

### 阶段 D：正式制卡适配

原始 PDF 交付已实现，八类模板有来源和版本。2026-09-08 默认升级为单 Agent、模板驱动的详细粗卡（rough-card-single-agent-v1），取消六角色、固定数量和人工复核交办，保留完整 PDF 阅读要求、归因与信息边界、Python 结构校验及安全写入。旧六角色只作兼容。

已完成离线回归测试，未代跑真实新卡；不能声称科研质量、主题收益或处理时长已验收。清理失败不覆盖模型结果，未校验输出先保存在本地。详见 [单 Agent 规则](single-agent-rough-card.md)。

### 阶段 E：Git、事件与无人值守

实现关键事件、Git 提交推送、失败重试、每日运行和开机补跑。日报只实现最小“新增、完成、阻塞”汇总。

### 阶段 F：砸电脑验收

在没有旧机器本地状态的环境中完成安装、全量对账、幂等重跑和自动调度恢复。

只有阶段 B、C、E、F 的技术验收通过，且阶段 D 完成单 Agent 真实试运行、异常恢复验证并如实记录质量边界，才能称“Zotero 到证据包”链路已经完成。
