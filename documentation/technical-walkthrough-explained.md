# 技术流程逐步解释：一篇论文如何从 Zotero 走到主题

这份是帮助你先弄懂的详细版，不是要求在黑板上逐字讲完。原来的[20分钟技术稿](mentor-blackboard-talk.md)保留作汇报提纲；本文最后会说明哪些必须讲、哪些留作答疑。

阅读顺序：先弄懂“谁负责什么”，再跟着一篇论文走一遍，最后看重复执行、失败、主题和定时运行。先不背函数名。

本文中的论文 A、B、C、缩写哈希 H1 和示意数据，只用于解释程序行为，不代表新做了一次真实运行，也不能复制进实际配置或任务文件。

## 1. 先分清：Zotero、Python 和 Codex 是三个不同角色

它们不是一个东西，只是由程序连接起来。

| 角色 | 实际负责什么 | 不负责什么 |
|---|---|---|
| Zotero | 保存论文条目、PDF 附件，以及它们之间的对应关系；将共享库资料同步到本机 | 不替本平台决定证据卡做完没有 |
| Python 程序 | 查资料、安排任务、调用模型、检查来源和保存状态、写文件、记进度 | 不凭自己的普通代码理解论文的科学结论 |
| Codex | 接收这次任务，调用本机工具读论文，按模板分析并返回结果 | 不充当整个系统长期唯一的任务记忆，也不直接决定正式成果写到哪里 |

可以把 Python 理解为“负责安排工作的程序”，把 Codex 理解为“被安排去读论文的执行者”。这只是角色比喻，实际是一段 Python 代码启动另一个程序，传入任务，再读取它的返回结果。

最重要的一点：**不是让当前聊天窗口记住哪篇做过，而是让程序把这些记录写进文件。** 换一段对话，甚至重新启动程序，它还可以读取记录继续工作。

向老师可以这样说：

> 我们没有把整条流程交给一个聊天窗口自由执行，而是用 Python 管理任务和文件状态，只有需要理解论文的步骤才调用 Codex。

## 2. 敲下这一条命令，电脑到底做了什么？

```powershell
python automation/run.py run-once --json
```

把它拆开看，不需要把它当成一串咒语：

| 这一段 | 意思 |
|---|---|
| `python` | 用 Python 解释器执行后面的程序文件 |
| `automation/run.py` | 项目的启动文件；它把工作交给命令行处理模块 |
| `run-once` | 本次选择“执行一轮完整流程”，而不是只检查环境或只查看任务 |
| `--json` | 最后的运行总结使用 JSON 格式，便于程序读取；它不是“开启自动化”的开关 |

进入程序后，有三件事先发生：

1. **理解命令。** 知道你要运行完整流程。
2. **读取配置。** 知道用哪个共享库、成果放哪里、调用哪个模型、最多等多久。
3. **检查同一本地工作区是否已经在跑。** 若已有完整流水线运行，就不再开第二轮去重复抢同一批任务。

随后才进入 Zotero 检查、任务同步、制卡和主题处理。

所谓“流水线”，就是代码里已经安排好步骤和分支。例如没有 PDF 时走等待分支，有完整卡时走复用分支，不是无论遇到什么都机械地执行下一步。

配置文件也不是运行记录。配置回答“按照什么规则运行”；任务文件回答“按照这些规则，目前做到哪里”。

向老师可以这样说：

> 一键运行背后是统一的调度函数。它先读取配置，再根据每篇论文的实际状态决定执行、跳过、等待还是停止，不需要人逐条输入分步命令。

## 3. Python 怎么看见 Zotero 里面的论文？

### 3.1 “本地 API”是什么意思？

API 可以理解成软件给其他程序提供的一个“按规定询问数据的入口”。

你用鼠标打开 Zotero 看文献，走的是人看的界面；Python 通过本地 API 询问 Zotero，走的是程序能读取的数据入口。程序不需要模拟点击每一篇论文。

当前配置里的地址是 `http://127.0.0.1:23119`：

- `127.0.0.1` 表示当前这台电脑，不是另一台服务器。
- `23119` 是这个服务的端口，可以理解为同一电脑上用来找到这个服务的入口编号。
- 群组编号 `6618088` 决定查询的是哪个共享库。

程序询问的大意是：“把这个群组当前的条目按页给我。”每页读一部分，读完再继续下一页。读取期间如果接口报告的条目总数或库版本改变，程序会拒绝把这份不完整清单当作可靠输入。

这部分不需要 AI。普通 Python 代码就可以完成列表读取和记录对照。

### 3.2 为什么要分父条目和附件？

Zotero 中看到的一篇论文，至少涉及两个层次：

```text
父条目：论文 A
  标题、作者、年份等信息
  父条目 Key
       │
       └─ PDF 附件
            附件自己的 Key
            对应哪个父条目
            原 PDF 在本机的文件位置
```

父条目像论文的“目录记录”，PDF 附件才是实际文件。**有目录记录，不等于 PDF 已经存在于当前电脑。**

因此程序先找到父条目，再找其 PDF 附件，最后检查附件对应的本机文件，而不是只要看见标题就制卡。

### 3.3 “发现新增”是不是只比较新标题？

不是。当前 `run-once` 会重新取得共享库的可见条目清单，再与本机任务表对照。

这不是每次重新让模型处理所有论文。要分开两种成本：

- **读取清单、检查文件、计算哈希：** 普通程序操作，有本机和接口开销。
- **调用模型阅读和生成：** 只对需要处理的任务执行，才涉及模型额度。

这样能处理一个很常见的情况：

> 今天论文 A 已入库，但没有 PDF；明天还是同一个父条目，只是补上 PDF。程序再检查时，能把它从等待转成就绪，而不会因为“它不是新标题”就永远漏掉。

独立 `scan` 命令还可以保存快照并报告新增条目、新增附件等变化。但完整入口直接同步任务，不需要你先手工执行 `scan`；它也不是靠 Zotero 主动推送通知。

向老师可以这样说：

> 我们通过 Zotero 本地接口读取父条目与附件对应关系，并把当前清单与任务表对账。因此既能处理新论文，也能发现旧论文后来补上的 PDF。

## 4. 论文 A 第一次入库，却没有 PDF：为什么系统不会乱做？

假设论文 A 刚进入共享库，但还没有附件。

程序已经知道有这篇论文，可以先建立任务记录。把这条记录翻译成人话，大致是：

```text
论文：A
属于哪个共享库：已知
父条目Key：已知
PDF附件：还没有
当前状态：等待PDF
已经尝试制卡几次：0
```

实际记录保存在本机的 `.runtime/tasks.json`，上述文字不是实际 JSON 格式。

这里不调用 Codex，不用摘要冒充全文，也不因为任务记录已经建立就声称卡片完成。

明天补上 PDF，程序还会检查：

1. 文件是不是已经下载到这台电脑，而不是只有附件图标？
2. 文件能不能打开读取，大小和 PDF 基本结构是否正常？
3. 是否存在多个 PDF，让主文件选择有歧义？
4. 当前 Zotero 全文索引是否满足程序的最低长度要求？

不同问题会留下不同原因。没有文件是等同步，不是认定模型失败；没有正文索引是等索引，不是反复制卡。当前没有自动 OCR，文本条件不满足时不能假定扫描版已可读。

满足条件后，任务变成 `READY_FOR_EXTRACTION`。翻译成中文就是“已具备处理条件”，**不是“已经把全文提取出来了”，更不是“已经完成证据卡了”。**

任务状态可以理解为贴在任务上的标签：

| 状态 | 用人话解释 | 后面可能怎么走 |
|---|---|---|
| 等待 PDF | 还没有原文件 | 下次补齐后重新检查 |
| 等待同步或索引 | 附件相关准备尚未完成 | 条件满足再进入就绪 |
| 就绪 | 可以安排制卡 | 领取任务，开始处理 |
| 处理中 | 已经有一个执行者领取 | 保存成功，或留下失败原因 |
| 已完成 | 任务记录标记完成 | 仍须结合真实证据包核对 |
| 待重试 | 上次未正常完成 | 原因允许、冷却结束且次数未超限才重试 |
| 阻塞 | 遇到不能自动解决的条件 | 保留现场，不随便跳过规则 |

“状态机”这个词，就是这些标签只能按照规定条件变化。例如还在等 PDF，不能直接跳到已完成。

## 5. 防止重复：先讲清三个编号和一种检查

### 5.1 父条目 Key：回答“是哪一条论文记录”

在同一个 Zotero 库里，父条目 Key 用于定位这一条记录。项目再带上群组 ID，避免混用不同库。

**论文身份 = 群组 ID + 父条目 Key。**

标题主要给人看，不能用作程序唯一身份。改标题不应导致同一条论文被当成一篇新论文再做一次。

### 5.2 附件 Key：回答“这条论文下面是哪一个文件记录”

一条论文可能有附件、补充材料等。附件 Key 用来区分具体的附件记录，不等于论文父条目的 Key。

因此不能拿 PDF 附件 Key 去替代要求父条目 Key 的命令参数。

### 5.3 PDF 哈希：回答“文件内容有没有变化”

哈希是程序读取文件内容后，按固定算法计算出的一串值，可以把它理解为“文件内容指纹”。当前使用 SHA-256。

比如，我们把第一次 PDF 的真实长哈希简称为 H1：

- 文件字节内容不变，重复计算仍得到 H1。
- 只换保存位置，内容未变，哈希不因此变化。
- 文件内容发生变化，哪怕文件名相同，通常也会得到不同哈希。

程序不需要读懂论文，就能比较 H1 和新算出的指纹是否一致。

但哈希不是论文的语义身份。两个排版不同的 PDF 可能是同一篇论文，却有不同哈希；更改 PDF 内部元数据也可能改变哈希。因此它用于判断本次输入文件是否变化，不等于做学术文献查重。

### 5.4 任务编号：把本次处理输入绑定起来

当前程序把下面四项按固定格式组合，再计算任务编号：

```text
群组ID + 父条目Key + 附件Key + PDF内容哈希
                       ↓
                   TASK-一串哈希
```

意思是：“这一次任务针对的是这个库里、这条论文下面、这个附件的这一份内容。”

它不以今天的日期或第几次运行命名，所以不会因为你明天再按一次命令，就天然变成一项全新任务。

注意：任务编号目前不是所有配置的总版本号。修改模型或粗卡模板，不会自动授权把已有有效粗卡重新生成。已有卡是否重做，是另一个需要明确规则的问题。

### 5.5 最关键的检查：不是看目录，而是核对真实成果

只有编号仍然不够，因为目录可能早就建好了，卡片却还是空占位。

当前会检查：

- `manifest.json` 和 `card.md` 是否存在且能读取。
- 清单是否是有效的已生成记录，而不是占位状态。
- 正文是否非空、不是占位内容。
- 重新计算的正文哈希，是否等于清单保存的正文哈希。
- 若清单声明了执行审计文件，它是否存在且内容指纹、状态能对应。
- 来源是否和当前这项任务一致。

这些条件匹配，才能把它当作已有成果复用。**不是检查卡片写得有多好，而是检查“这份确实已经保存的成果，是否就是这项任务对应的成果”。**

若正文被人改过、来源变了或文件缺失，程序保留内容并报不一致，不通过覆盖旧文件来强行修复。

向老师可以这样说：

> 防重分成身份定位和成果核对两部分。Key 确定是哪条文献，PDF 哈希确定是哪份输入，正文和清单的一致性确认有没有真实完成；不是用文件夹是否存在来判断。

## 6. tasks.json、manifest.json 和 card.md：为什么要有三份？

这三个文件记录的不是同一件事。

| 文件 | 你可以把它当成什么 | 主要回答什么问题 |
|---|---|---|
| `.runtime/tasks.json` | 当前电脑的工作进度表 | 哪些等文件、哪些处理中、试过几次、为什么失败？ |
| 证据包里的 `manifest.json` | 这份成果附带的来源与版本说明 | 对应哪条论文、哪个 PDF、用哪个模型和模板生成、正文指纹是什么？ |
| 证据包里的 `card.md` | 真正生成的阅读内容 | 研究问题、数据、方法、结果和分析到底写了什么？ |

新流程还会保存 `quality-audit.json`，记录执行和流程检查。名字里有 quality，不代表它做过独立科学审稿。部分旧版有效卡片没有这个文件，不能用新目录示意反推所有历史卡都必须长得一样。

举一个能看出差别的例子：

> 模型已经完成，card 和 manifest 已保存，电脑却在更新 tasks 之前断电。

下次运行可能看到：“进度表还没标完成，但成果已经完整存在。”程序核对成果后，可以补齐任务状态，而不是再读一次论文。

反过来，如果 tasks 写着完成，但文件丢了，程序不能只相信进度表。它会指出不一致，而不是当作成功。

这就叫“对账”：**把工作记录和实际文件互相核对。**

换电脑也用得上这个区别。已经提交的证据包跟着 Git 过来，里面带着来源和生成记录，可以帮助新电脑重建自己的任务状态；新电脑不需要依赖原电脑聊天窗口的记忆。

## 7. 防重和防“两个程序同时做”不是一回事

前面解决的是“上次做过，本次不要再做”。这里解决的是“两个人或两个进程几乎同时按了运行”。

### 7.1 整轮锁：同一工作区只让一轮完整流程先跑

如果手动运行还没结束，定时器又触发，第二轮发现同一本地工作区已经被占用，就返回“已有运行实例”。

可以把它理解为入口处的占用标记，但当前整轮锁由操作系统持有，不只是随便写一个“忙”字。进程退出时，操作系统会释放该锁。

### 7.2 状态写入锁：避免两边同时改任务表

修改任务表前先取得短时间的写入权。否则两个进程都读到旧内容，再分别保存自己的结果，就可能把对方的更新盖掉。

它保护的是记录更新，不是替模型阅读。

### 7.3 单篇租约：说明“这篇目前由谁领取”

领取任务时，程序记录领取时间、到期时间和一个令牌，同时将状态改成处理中。令牌可以理解为这次领取的凭据，完成时要对应得上。

租约有有效期，是为了避免执行者崩溃后，记录永远卡在“有人正在做”。过期后进入后续对账和重试判断，不代表一到期就立即无条件开第二个模型任务。

当前租约为 30 分钟，单次生成上限为 25 分钟；两者用途不同。还要结合整轮锁、实际成果和重试条件判断。

这些保护都围绕同一个本地工作区，**不是跨两台电脑共享的分布式锁，也不是谁有权制卡的账号权限系统。** 当前生产上仍需要遵守指定主机运行的约定。

## 8. 真正开始制卡：Python 交给 Codex 的是什么？

先记一句话：**交付的是一次明确任务，不只是一个文件名。**

### 8.1 准备任务材料

Python 会把下列内容组合起来：

| 材料 | 举例或作用 |
|---|---|
| 原 PDF 的本机路径 | 告诉执行者去哪读真正的文件 |
| 来源身份 | 群组、父 Key、附件 Key、PDF 指纹 |
| 阅读和制卡提示词 | 要读哪些内容、如何区分原文陈述与 AI 推理 |
| 已启用的论文类型模板 | 由 Codex 在本次会话中选择适用类型并填写 |
| 输出结构要求 | 结果怎样组织，Python 才能稳定接收 |
| 本机工具及工作目录 | 文字提取、PDF 信息、页面渲染工具在哪里；临时文件放哪里 |
| 模型运行参数 | 模型、推理强度、时限、子进程代理 |

“提示词”是告诉模型要完成什么工作的文字。“模板”是希望正文按什么内容结构写。这两者不等于程序的防重规则：模型是否重复领取，不靠一句“不要重复”来解决，而由外面的任务和文件检查控制。

### 8.2 “适配器”不是另一个智能体

适配器就是一层专门负责和模型工具打交道的代码。

流水线只需要表达：“请对这份输入生成结果。”适配器负责把这个要求转换成 Codex 命令行接受的参数，启动程序，再把结果转回来。

```text
流水线：需要一份证据卡
          ↓
适配代码：整理参数，启动 Codex CLI
          ↓
Codex：执行阅读与生成
          ↓
适配代码：接收事件、结果或错误
          ↓
流水线：继续保存，或者登记失败
```

当前已经实现的是 Codex 这条接入路径。换它支持的模型名称可以改配置；要接另一家完全不同的服务，还需要写相应适配代码，不能把不存在的适配器名称填进配置就算接入成功。

### 8.3 “子进程”是什么意思？

Python 程序在运行时，启动另一个独立执行的 Codex 命令行程序。这个被启动的程序叫子进程。

因此不是让你在桌面聊天窗口里手动粘贴任务。Python 会等待这个子进程返回，并观察它输出的事件：开始调用工具、命令结束、模型回合结束、报错等。

当前用本机已登录的 Codex 订阅账号。配置里的代理只作用于本平台启动的模型子进程，不替你改全局 VPN 或桌面客户端设置。

### 8.4 给了路径，Codex 怎么看到文字和图？

本机路径不是互联网下载链接，远端模型不会凭空拥有那个磁盘文件。需要 Codex 的本机执行工具来读取。

当前可用的实现是：

1. 用本地工具确认 PDF 页数及读取环境可用。
2. Codex 按任务调用 Python 的 `pypdf` 等本机工具提取文字。
3. 用 Poppler 的页面渲染工具把 PDF 页面转为图片。
4. 通过看图工具查看生成的页面图像，处理图表内容。

当前制卡链路不再启动之前的 PDF MCP。临时文字和页面图片可以写进独立工作区，原 PDF 保持在 Zotero 存储位置，正式知识目录的写入由外面的 Python 管理。

**“不复制原 PDF 到 Git 仓库”，不等于“完全不产生临时文字或图片”。** 后者是本机工具帮助模型读取 PDF 时可能产生的中间材料。

读取经过和模型阅读报告会留下记录，但这些记录不等于逐页理解和科学正确性已经被独立证实。

### 8.5 为什么让模型返回 JSON，里面又有 Markdown？

两者用途不同：

- **Markdown：** 适合保存可读的卡片正文，标题、段落和表格都能表达。
- **JSON：** 适合程序区分“这部分是模板编号，那部分是正文，这部分是阅读报告”。

可以理解为“一个有标签的包裹，里面装着 Markdown 文档”。简化示意如下，不是实际完整返回结构：

```text
模板编号：某种论文类型
阅读报告：文字和图像的处理情况
卡片正文：一段 Markdown
```

Python 接到包裹后，从正文这一栏拿出 Markdown，保存成 `card.md`；其他信息进入对应生成记录。

这不是重新把正文写法卡得很死。当前仍要求基本数据能解析、来源能对应、正文非空，但不因少一个固定标签或调整了 Markdown 标题顺序就拒绝整篇卡。

向老师可以这样说：

> Python 通过适配器启动 Codex 独立会话，提供原 PDF 路径、读取工具、模板和任务要求。Codex 返回结构化结果，正文由 Python 取出并保存，模型不直接修改正式成果目录。

## 9. 保存为什么还要做那么多步骤？用一次断电说明

### 9.1 最容易理解的正常过程

模型完成后，当前新粗卡通常要保存正文、来源清单和执行审计，再更新任务表。

如果只写 `card.md`，写到一半断电，可能得到半张卡。如果正文写好了、清单没写好，也可能出现文件之间不一致。

所以“模型输出成功”和“成果保存完成”必须分成两件事。

### 9.2 临时文件解决“一个文件写到一半”

程序先把完整内容写入临时文件，完成检查后，再用它替换正式文件。这一步叫“原子替换”。

你可以理解为：先把新纸完整写好，再替换文件夹里的旧纸，而不是直接拿旧纸写到一半停电。

在系统提供的替换保证范围内，读者不会因为正文写到一半而看到逐字增长的正式文件。但磁盘、权限等错误仍然可能导致操作失败。

### 9.3 待发布记录解决“几个文件没有同时写完”

单文件替换不能让三个文件天然同时成功。程序还在替换前，把准备发布的内容和来源写进 `.runtime/pending-publications/`。

这份记录包含拟保存的卡片、清单和审计等内容，不只是写一个“准备好了”的标记。

```text
收到完整模型结果
      ↓
准备临时文件、检查内容和来源
      ↓
保存待发布记录
      ↓
替换审计文件 → 替换card → 替换manifest
      ↓
更新任务表：完成
```

如果其中发生中断，下次在允许对账的条件下，可以按照待发布记录核对现场、补齐文件。

| 中断位置 | 现场可能有什么 | 是否能不重新调用 AI？ |
|---|---|---|
| 模型还没返回完整结果 | 没有可接受的完整输出 | 不能承诺，通常还需要后续重新尝试 |
| 完整待发布记录已保存，正式文件只替换一部分 | 有明确的拟发布内容 | 来源和现有文件匹配时，可补齐保存 |
| 正式成果完整，任务表没标完成 | 有可核验的 card 和 manifest | 对账后可补任务状态 |
| 期间有人改过正文或换了输入 | 恢复记录与现场不一致 | 不能直接覆盖，保留文件并报告冲突 |

如果旧任务租约仍有效，下一轮可能先等待；不是任何中断都能立刻恢复，更不是恢复远端模型尚未说出来的想法。

这套机制叫“故障恢复”，不是“永不失败”。它的具体价值是：**已经生成并妥善记录的结果，不必只因为最后保存或记账中断就全部重新生成。**

`.runtime/generation-drafts/` 的草稿与待发布记录也不同。前者可能只是尚未验收的模型输出，不能看到里面有文字就直接算正式卡；仅符合已有恢复条件的草稿才能走恢复路径。

## 10. 一键处理多篇，到底是在循环什么？

现在假设本轮有三篇：

- 论文 A：以前已经生成过有效证据卡。
- 论文 B：刚补好 PDF，尚未制卡。
- 论文 C：只有父条目，还没有 PDF 附件。

程序的决策是：

| 论文 | 本轮判断 | 实际动作 |
|---|---|---|
| A | 来源与已有完整成果一致 | 复用，跳过制卡模型 |
| B | 输入就绪、没有完整卡 | 领取任务 → 调用 Codex → 保存 → 标记完成 |
| C | 没有原 PDF | 记录等待，不调用制卡模型 |

这张表就是任务循环的核心：每次看一项，作判断，执行允许的动作，再看下一项。它不是让一个模型拿着整份清单随意决定文件操作。

当前是串行，一篇完成保存后再处理下一篇；默认不要求每处理几篇就人工改配置。运行开始时取得的队列不是实时滚动刷新，运行途中新增通常到下一轮才进入。

本轮结束时会有总报告。上面例子可以出现“新完成一篇、跳过一篇、等待一篇”；它不是“全部三篇都完成”。即使其中一条终端消息显示保存成功，也不能拿它代表整轮结果。

如果论文 B 失败，是否继续处理后面任务还看错误类型：

- 某篇自己的文件或局部处理问题，不撤销其他已经保存的成果。
- 模型账号、额度或服务整体不可用，会让后续生成任务延后，避免每篇都撞同一种问题。
- 暂时性错误也要符合冷却与尝试次数限制，不无限循环。

当前单次模型生成上限 25 分钟、单篇同一输入最多尝试 3 次、可重试任务冷却 1 小时。进度心跳每分钟一次，工具和保存事件即时报告。心跳表示本地仍在等待，不代表远端模型肯定正常。

是否继续主题也要看本轮状态。**单纯还没有添加 PDF 的论文 C，不必然阻塞已有粗卡的主题；已存在附件但同步未就绪、模型失败或其他阻塞等情况，会使主题暂缓。** 程序保留这种区分，不把所有等待都当作同一种失败。

## 11. 从粗卡到主题：不是“把几张卡合成一段话”

### 11.1 “统一文献池”在代码里是什么？

目前不是额外建立了一座数据库。程序扫描 `evidence-packs/` 下的证据包，选择当前群组里通过完整性检查的粗卡，在本轮内存中组织成可用来源集合。

假设前天生成 A、B 两张卡，今天生成 C：主题步骤考虑的仍然可以是 A、B、C，而不是只看今天这一张。运行批次是运行记录，不是知识分组边界。

### 11.2 第一次模型调用：先形成可执行的计划

程序把以下材料交给主题规划步骤：

- 全部有效粗卡。
- 现有主题和它们的状态。
- 已保存、来源仍匹配的精读。
- 可选的研究目标，没有目标也可以运行。

规划结果不只有一篇文字，还包括程序能读取的“接下来做什么”。例如下面是中文教学示意，不是实际 JSON：

```text
候选主题：T
相关论文：A、C
论文A：重点看模型如何表示时间变化
论文C：重点看结果适用条件
已有精读：若适用，指定复用的记录及理由
```

候选正文先存为 `initial.md`，相关工作安排存入计划记录。模型提出引用的证据 ID，程序核对这些 ID 是否真的属于当前来源，不让模型随意指定磁盘路径。

### 11.3 第二阶段：按计划定向精读

Python 根据计划里的证据 ID，找到对应证据包，再根据来源找到 Zotero 原 PDF。

此时给 Codex 的任务不再是“全面做一张粗卡”，而是“围绕候选 T 的这个问题，重新读取原论文并详细解释”。

结果仍放回论文自己的证据包，例如论文 A 的 `readings/某个记录/reading.md`。粗卡保留，定向精读增加在旁边，**不是把粗卡覆盖成只服务主题 T 的一张窄卡。**

同一论文服务另一个问题时，可以有另一份精读。多个主题若使用同一份适用精读，就引用它，不需要复制文件。

### 11.4 第三阶段：用精读结果修订候选

精读齐备后，Python 再把初版候选、精读结果和相关历史主题交给回填步骤，得到 `revised.md`。

这里的“回填”是用新分析修订初版认识，不是恢复旧版本。哪些关系被支持、哪些应收窄、哪些应撤回，由模型在修订中表达；程序负责把初版和修订版都留下。

因此一条来源关系可以表示为：

```text
修订主题T
   ├─ 引用论文A的定向精读 → A的证据包 → A的原PDF身份
   └─ 引用论文C的定向精读 → C的证据包 → C的原PDF身份
```

文件身份和引用可以被程序核对，科学判断是否成立不能仅由这条链接证明。

### 11.5 “输入指纹”和“检查点”分别解决什么？

主题的输入指纹不只是 PDF 哈希，它还组合粗卡来源和内容、研究目标、模型与提示词等。程序先问：“这次需要处理的条件，和上次成功处理的一样吗？”

- 一样：直接复用已有主题，不再调用规划模型。
- 不一样：进入规划，再决定新增、修改或复用哪些内容。

模型、目标或提示词改了，即使没有新论文，也可能触发新一轮主题处理。

检查点则是“某一步已经完成，结果和输入一起存下来了”。例如：

```text
规划完成并保存
    ↓
论文A精读完成并保存
    ↓
论文C精读完成并保存
    ↓
主题回填失败
```

再次执行时，输入和记录都匹配，就可以复用前三步已有结果，继续完成后续，而不是必须从规划开始全部重跑。若输入或记录冲突，则不能冒充同一个已完成步骤。

这叫步骤级续跑，不是把被中断的模型会话从同一句内部推理继续播放。

### 11.6 更新、合并、拆分后怎么不丢历史？

`themes/_registry.json` 可以理解为主题池的总目录：每个主题编号是什么、现在指向哪个版本、从哪些主题演变而来。

| 动作 | 文件和身份怎样处理 |
|---|---|
| 补充或修正 | 沿用主题编号，保存新版本，旧版本保留 |
| 合并 | 新建主题编号，保留原主题，并记录前后关系 |
| 拆分 | 创建新主题编号，保留被拆分主题及来源关系 |

一次变更所需结果都完成后，程序先保存本地变更提交记录，再更新注册表和阅读索引。中途失败时，旧的当前主题不被一套尚未完成的新结果替换。

这里“提交”不是 Git 的 commit。文件保存在本地，不等于已经上传 GitHub。

已有正式主题不允许被自动演化流程直接覆盖；当前还没有专用的正式确认操作入口。不要把修订候选说成系统已经自动批准的正式主题。

向老师可以这样说：

> 主题阶段先输出计划，再由 Python 按计划找到原 PDF 做精读或复用，最后把精读结果交给回填步骤。每步结果绑定输入保存，主题总目录指向当前版本，旧版本和引用关系都保留。

## 12. 从“一键”到“每天自动”：只是在入口外加了一个定时检查

手动执行时，由你启动 `run-once`；定时执行时，由 Windows 计划启动项目的调度入口，再由调度入口判断是否需要调用同一个完整流程。

```text
你手动输入命令 ─────────────────┐
                               ↓
                         同一个 run_once
                               ↑
Windows计划 → 检查是否到期 ─────┘
```

这样扫描、防重、制卡和保存规则只需要维护一套，不会出现手动路径修好了、定时路径还在用另一套旧代码。

当前配置有三个容易混淆的时间：

| 时间 | 含义 | 不代表什么 |
|---|---|---|
| 每天 09:00 | 新的每日任务时段到期 | 不保证关机时也能运行 |
| 每 30 分钟 | 唤醒做一次到期和补跑条件检查 | 不代表每半小时都重新制卡或扫描新论文 |
| 补跑冷却 60 分钟 | 失败或等待后再次尝试的调度条件之一 | 不代表到了时间就无条件忽略错误 |

程序把这一天的状态写在 `.runtime/scheduler-state.json`。如果该时段已经完成，后续检查就退出；若失败或等待，还要看冷却与每日尝试上限。

例如，上午本日任务成功，下午新加一篇论文：当前实现可以由你手动再跑一轮，否则通常等下一每日时段。它不是随时监听新增的实时服务。

安装也分两步：

1. 配置写明想怎么调度。
2. 安装命令把对应任务注册到 Windows，再用状态命令确认实际注册情况。

只改 JSON 的启用开关，不等于系统里已经安装了新计划。换电脑也要按新位置重新检查和安装，不能沿用旧电脑的计划任务路径。

## 13. 配置化、换机恢复和工程化，到底分别是什么？

### 13.1 配置化：变化的信息集中放，不在各处散落

拿模型时限作例子：

> 配置里填写 1500 秒，程序读取后把这个值交给模型执行层。换成别的允许值，后续启动就按新值运行，不需要逐个找业务函数中的数字修改。

类似信息包括共享库编号、成果目录、模型、思考强度、子进程代理、时限和调度。

相对路径也容易误解：当前配置里项目根的 `..` 相对于配置文件所在目录解析；成果目录等再相对于项目根定位。不是一律相对于你打开 PowerShell 时所在的位置。

但配置不是万能的：

- 改模型名字，账号和工具仍须真正支持该模型。
- 改路径，目标位置仍须存在或可建立，并有需要的权限。
- 更换服务商，需要对应的适配实现。
- 更换群组，不能混用旧群组的成果和运行状态。
- 密码、登录令牌不能为了方便一起上传进配置。

### 13.2 换机恢复：有三类东西要分别恢复

| 类别 | 从哪里来 | 例子 |
|---|---|---|
| 程序和共享知识 | Git 仓库中已经提交的内容 | 代码、模板、配置结构、证据包、主题、历史记录 |
| 原始文献文件 | Zotero 同步及本机附件下载 | 论文 PDF |
| 本机执行环境和身份 | 安装脚本与这台电脑的账号授权 | Python 依赖、PDF 工具、Codex 登录、文件权限、Windows 计划 |

“依赖”是程序需要使用的其他软件库或工具；“依赖锁”记录经项目选定的具体版本或制品信息，安装脚本据此准备环境。

`setup` 把相关预检、项目依赖安装、状态恢复等步骤组织起来，但不替人凭空取得共享库权限，也不替人完成所有账号登录和首次系统授权。

恢复任务时，程序核对共享证据包里的来源和完成记录，再建立或对齐本机任务表。所以换机目标是“相同规则能继续执行”，不是保证模型逐字复现旧答案。

已经上传的成果可从 Git 恢复；没有上传的本地成果和未发布草稿，不能指望新电脑自动拥有。`.runtime` 中有恢复材料，不能为了重装随手全部删除。

### 13.3 “工程化”不是增加很多文件，而是这些条件有了实现

| 以前容易靠人完成的事 | 当前交给程序的具体部分 |
|---|---|
| 记住哪篇做过 | 任务表与有效证据包对账 |
| 记住该执行哪一步 | 统一入口中的状态判断和调用顺序 |
| 拿到结果后手工复制 | 模型输出解析与受控保存 |
| 保存失败就全部重来 | 待发布记录与已完成步骤复用 |
| 不知道卡在哪里 | 阶段事件、等待心跳、错误原因、总报告 |
| 换电脑到处改代码 | 总配置、依赖安装、来源核对与任务恢复 |
| 天天手动触发 | Windows 计划调用同一条核心流程 |
| 规则改坏了才发现 | 对重复、状态、保存中断和主题版本等行为编写测试 |

这不是说所有事情都不需要人。网络、权限、冲突或不支持的输入仍可能阻塞，科研判断也不因为程序测试通过就自动正确。

向老师可以这样说：

> 工程化的具体体现，是把运行规则、状态记录、保存恢复和环境配置从人工操作中分离出来，写进可重复执行的程序，并为关键异常情况建立测试。

## 14. 现在把整条链用人话重新讲一遍

下面这段先用来检验自己是否理解，熟悉后可以作为汇报的串场，不用逐个背技术名词。

> 我先把论文放进共享 Zotero。运行时，Python 问本机 Zotero 有哪些论文、各自有哪些 PDF，再检查这些文件是否真的可以在本机读取。
>
> 有论文但没文件的，先记成等待；已经有完整卡片的，核对以后跳过。需要新做的，则记下这次针对哪个条目、哪个附件和哪一份 PDF，再安排模型任务。
>
> Python 把原 PDF 位置、模板、任务要求和本机工具信息交给 Codex。Codex 用工具读取文字和页面图像，在一个制卡会话里完成类型判断与分析，返回带有正文和生成信息的结果。
>
> Python 不把模型回复直接当作完成，而是核对来源和结果，准备正式文件，并保留必要的恢复记录。文件保存以后，再把任务记成完成。下一次还是同一份输入、同一份完整成果，就不用重做。
>
> 主题步骤再读取整个有效粗卡集合和已有主题，先形成计划，再按计划对相关原文精读或复用旧精读。精读放回对应论文的证据包，修订后的主题保留引用、版本和演化关系。
>
> 每一轮用同一个入口执行，计划任务也调用这条入口。各类位置和模型参数从配置读取，环境用安装脚本准备，所以日常操作才能变成一条命令。

## 15. 明天 20 分钟怎么讲：只保留这六个问题

详细理解版不要整篇念。黑板和时间建议如下，剩余技术细节留作答疑：

| 时段 | 老师需要听懂的问题 | 你在黑板上写什么 | 详细版对应 |

| 0–2 分钟 | 谁安排工作，谁读论文？一条命令从哪进？ | Zotero / Python / Codex；run-once | 第 1–2 节 |

## 16. 用四个场景检查自己有没有理解

### 场景一：只给 Zotero 改了论文标题，要重新制卡吗？

答：标题不是唯一身份。同一父条目、同一附件和输入内容，已有成果仍匹配时，不因为标题变化就重新制卡。

### 场景二：有证据包文件夹，但 card 只有占位内容，算完成吗？

答：不算。目录可能先建好，必须看实际正文、来源与生成记录。缺文件或互相矛盾会报告异常，不靠目录数量统计完成。

### 场景三：模型结果和正式文件已保存，但完成状态没写上，怎么办？

答：程序在允许对账时核对已保存成果，符合条件可以补齐任务状态。若有未过期租约会先等待；不能仅因表里没写完成就立即再开一轮模型。

### 场景四：新来一篇 C，之前的 A、B 会参与主题吗？

答：会作为全池来源参与规划，不受本轮生成批次限制。A、B 的有效粗卡不用重制，相关精读可按适用性和记录条件复用；有新问题才安排必要的新精读。
