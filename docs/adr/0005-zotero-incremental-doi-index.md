# ADR-0005：Zotero 查重索引改为带水位线的增量同步

## 状态

已采纳（2026-10-18）。

## 背景

`zotero_sync` 在创建条目前要回答一个问题：这个 DOI 在库里已经有了吗？

Zotero Web API 的 `q` 快速搜索**不索引 DOI 字段**，`qmode=everything` 只额外覆盖全文，
所以服务端无法按 DOI 过滤。项目因此维护一个本地账本 `.zotero-sync-index.json`。

问题出在**未命中**：账本只记录本流水线建过的条目，Zotero 桌面端、Beaver 导入器、
容器流水线建的条目都不在里面，所以"未命中"不能直接当成"不存在"，旧实现一律退回全库扫描。

代价是结构性的：库里有 5,938 个 DOI，分页 100 条一页，就是约 60 次串行 GET，
每次返回整条记录（标题、作者、摘要、标签……），实测约 5 分钟。而**每个新 DOI 必然未命中**，
所以"下载一篇新论文"这条最常见的路径永远付这笔钱。

## 决策

给账本加一条**库水位线** `last_version`（Zotero API 的 `Last-Modified-Version`），
把"未命中"从一个无法验证的否定变成一个可验证的结论：

1. 全量扫描时**先**读水位 V，再扫描，然后存 V。
2. 未命中时先读当前水位：
   - 等于账本水位 → 窗口内没有任何增删改 → **未命中即权威**，返回"不存在"；
   - 大于账本水位 → 拉 `top(since=V)` 与 `deleted(since=V)` 增量，合并后更新水位；
   - 小于账本水位 → 换库或还原备份，全量重建。
3. 增量失败 → 全量重建一次（宁可慢，不可错判为不存在而造出重复条目）。

水位必须在**拉取之前**读取：若在拉取之后读，拉取期间被修改的条目其版本号会落在
"比扫描新、比水位旧"的区间里，此后永远不会被重放。

## 取舍

- **首次升级仍要扫一次全库**（约 5 分钟）。没有别的方法能证明"账本之外的条目都不存在"；
  这一次扫描同时建立水位，之后每次未命中降到 1 次请求。
- **命中仍然是零请求**，即使库之后发生了改动——陈旧命中会在下一次未命中触发增量时被修正。
- 索引写入改为原子写（`.tmp` + `os.replace`），因为该文件位于 Google Drive 同步目录，
  部分写入会留下损坏的 JSON。
- 查重提前到 `build_item()` 之前：给已存在条目补挂 PDF 时不再付 Crossref 延迟，
  Crossref 故障也不再挡住补挂。

## 后果

- 稳态：新 DOI 入库的查重从约 5 分钟降到约 1 秒。
- v1 索引文件仍可读（视为水位 0），触发一次迁移扫描。
- 索引损坏、删除、`--refresh-index` 都回到"重建一次"的路径，行为可预期。

## 补充（2026-10-19）

- 索引除 `last_version` 外还记录 `library_id`。账本来自另一个库（换账号/换库）时
  水位线不可比，直接重建，避免把外来 key 当成命中。
- 增量读取用 `top(since=…, includeTrashed=1)`：**移到回收站是一次条目更新**
  （`data.deleted=1`），而不是 `/deleted` 记录。不带这个参数，账本里的陈旧命中永不失效。
  合并时丢弃 `data.deleted` 为真的条目。
- `since` 增量按 100 条分页，所以"3 次请求"是最小值；改动多时会更多。
