# [T09] 修复第一轮最影响使用的 1—3 个问题并复验

里程碑：M2 ｜ 认领角色：按问题认领的整理同学；同伴复验；导师确认取舍 ｜ 建议工作量：D8—D14 内按真实问题拆分估算

状态：待认领。GitHub Assignee、实际日期、验收结果以对应 Issue 为准；本文为创建时的任务定义。

## 为什么做
第二周投入应由第一周暴露的障碍决定，让产品在相同场景下变得更可用。

## 输入与前置依赖
T08 的真实失败清单、证据及优先级决定。T08 未完成前仅做任务准备。

前置任务：[T08](T08.md)

## 做什么
选择 1—3 个高优先真实问题，逐个明确修复范围与验收；需要多人或超过一天的工作拆为子 Issue，再实现并按原触发步骤复验。保留修复前后记录。

## 交付物
- 被选问题与选择理由、子任务（如需）及对应 PR。
- 同场景修复前后对照、同伴复验和残留问题。
- 第二轮结论：继续扩展、继续修复或暂缓。

## 完成标准
- [ ] 每项修复回链一个真实问题，具有复现步骤和明确完成条件。
- [ ] 没有优先级决定时不开始扩展功能；没有真实问题时记录无需本轮修复的理由并由导师确认。
- [ ] 每项修复均由同伴按原场景复验，确认问题消失且来源边界未破坏。
- [ ] 如果声称省时，提供同质量可比记录；否则只报告修复的具体障碍。
- [ ] 尚未解决的问题保持开启，并注明影响和下一步；不以总文件数作为完成标准。

## 不在本任务范围
不借迭代迁移整个知识库，不扩大材料范围或把未验证的新功能列作已完成。

## 受阻时怎么处理
问题无法稳定复现时先补最小复现材料；没有证据时不盲改核心架构。

## 如何提交与验收
认领后填写一位整理同学、一位同伴检查同学及预计交付日。交付候选文件或 PR 链接、基准版本和逐项证据；检查者写明结果。涉及科研取舍的事项由导师确认。仅创建文件或合并文档 PR 不关闭本 Issue。

关联旧需求：无直接对应的旧功能单。 旧单保留为能力方向；本单只验收当前小样本闭环的一个交付，不代表旧单的全部范围完成。
