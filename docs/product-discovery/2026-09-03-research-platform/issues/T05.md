# [T05] 跑通带来源的学习对话、按需补读和修改建议

里程碑：M1 ｜ 认领角色：工具整理同学；同伴检查同学复现；导师判断涉及的科研变化 ｜ 建议工作量：约 1 天

状态：待认领。GitHub Assignee、实际日期、验收结果以对应 Issue 为准；本文为创建时的任务定义。

## 为什么做
知识应能被追问和纠正，用户需要知道答案来自哪里，以及新材料为何改变原有表述。

## 输入与前置依赖
候选主题页、关联卡片与可访问原文、产品文档第 4.2 和 6.3 节、现有写回边界。

前置任务：[T04](T04.md)

## 做什么
交付可复制的 Codex 操作短句及必要连接说明。演示一次卡片已足够的回答和一次真实判断缺口驱动的定向补读，输出“原表述—建议表述—依据—影响范围”。先在候选范围展示差异，不自动应用正式多文件修改。

## 交付物
- 两次脱敏对话记录、使用的来源范围、补读问题及停止条件。
- 原卡候选修订、受影响主题清单和逐项修改建议；引用未受影响的主题也注明无需修改。
- 明确的执行结果：仅建议、候选已保存、正式已应用或失败；按实际发生填写。

## 完成标准
- [ ] 回答列出实际使用的来源及位置；无法访问全文时明确说出。
- [ ] 已有材料足够时不重复开补读；缺口会影响当前判断时才定位最小材料。
- [ ] 补读后仍不足时保留未知，不强造结论。
- [ ] 共享卡片变化只生成下游影响建议，不自动改写全部主题。
- [ ] 演示基准版本过期情形：停止覆盖、重新比对并给出差异。
- [ ] 候选写入可恢复；正式写回需要的授权或能力不具备时停在只读计划，且界面不显示“已生效”。

## 不在本任务范围
不开发全自动科研代理，不绕过正式写回合同，不将用户问一句视为所有正式文件获准修改。

## 受阻时怎么处理
没有真实补读触发点时先交付足够材料场景，补读部分标未验证并说明；不得用演示数据冒充科学增量。

## 如何提交与验收
认领后填写一位整理同学、一位同伴检查同学及预计交付日。交付候选文件或 PR 链接、基准版本和逐项证据；检查者写明结果。涉及科研取舍的事项由导师确认。仅创建文件或合并文档 PR 不关闭本 Issue。

关联旧需求：[#1](https://github.com/iHeadWater/mylibrary/issues/1)、[#2](https://github.com/iHeadWater/mylibrary/issues/2)、[#9](https://github.com/iHeadWater/mylibrary/issues/9) 旧单保留为能力方向；本单只验收当前小样本闭环的一个交付，不代表旧单的全部范围完成。
