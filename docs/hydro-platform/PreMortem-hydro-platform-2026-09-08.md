# hydro-platform 整体评估与失败预演

后续实施状态：US-11A 已针对下述多文件中断风险增加本地待保存记录、恢复补写和任务完成对账，并接入统一入口及整轮进程锁；新增中断和重复运行测试已通过。旧版没有完整待保存记录的半成品仍需保留阻塞，不能伪造恢复。详见 [统一运行](run-once.md)。下文保留当时诊断，旧代码行号不再对应当前版本；每日调度、真实运行验收和换机安装尚未完成。

评估日期：2026-09-08。范围：仓库架构、Zotero→证据包代码、配置、模板、操作与恢复文档。依据：已完整阅读的 PRD、实际执行入口、离线测试和下述临时数据实验。未调用真实模型，未改变 Zotero、正式证据包、网络、计划任务或 GitHub。

使用“意图与实现核对”区分设计目标与已交付能力，再用 pre-mortem 按真实风险、过度担忧、待验证假设分类。假设两周后尝试无人值守上线并失败，从失败倒推缺口；这不是已经确定的上线日期。

## 结论

主干合理，不建议重新推翻目录和数据归属：Zotero 保存论文与原 PDF，一个共享证据包对应一个父条目，Python 负责状态/校验/保存，Agent 负责阅读与内容生成，主题只引用证据包。单 Agent、模板驱动的详细粗卡更符合当前人力和时间约束。

但目前是“可以手动串联的单篇处理工具”，不是已经完成每日调度、故障恢复和换机部署的平台。下一优先级是运行闭环与产物一致性，不是再增加 Agent 数量。

## 本次已完成与保留边界

验证结果：254 项离线测试通过，八类模板静态校验和无模型 Codex CLI/读取依赖预检通过；不等于完整平台已验收。

- 默认 workflow_mode=single_agent；一次提供者调用，主提示词 v6、八类模板 1.1.0，来源 commit/blob 保留。
- 原文陈述、原文转述、AI 推理、信息边界分开；去除人工复核交办、摘录及固定数量门槛。
- 自动选型、完整原 PDF 读取要求、来源绑定、结构检查、已有卡跳过等保护仍在。归因格式检查不能证明语义正确。
- 模型返回后先存本地未校验草稿；临时目录清理失败不再覆盖模型结果。它不是断点续跑，也不能恢复未返回的内容。
- 历史六角色及原有卡片未删除/重写。STRUCTURE_VALIDATED 不冒充独立科学验证。
- 单 Agent 真实卡片效果与实际用时尚未测试；不能承诺固定分钟数或特定期刊等级。

## Tigers：真实风险

### P0 / 无人值守上线前：多文件写入中断可能被误判为已有卡

代码先替换 card.md，再替换 manifest.json：`hydro-platform/automation/src/hydro_platform/card_generation.py` 第 759、762 行。正常 OSError 有回滚，但中断并不等于普通异常。第 283 行又把“正文不等于占位卡”直接当作跳过依据。

在完全独立的临时测试目录中，模拟卡片已写入、manifest 发布前 KeyboardInterrupt，结果：

```json
{
  "manifest_card_status_after_interrupt": "PLACEHOLDER",
  "audit_exists": false,
  "next_generate_action": "SKIPPED_EXISTING_CARD"
}
```

这证明仍可能留下“有卡正文、清单还是占位、审计缺失”的半成品，然后被当作已有卡跳过。没有修改或模拟中断用户真实文件。

建议：增加可恢复的发布事务/完成标记；跳过前核对 card、manifest、audit 哈希及状态。遇到半成品先对账修复或明确报 PACKAGE_INCONSISTENT，不能重跑模型或覆盖未知人工内容。优先于接入每日调度。本次只发现和验证，尚未实施此修复。

### P1 / 无人值守上线前：缺少统一运行与恢复入口

`hydro-platform/automation/src/hydro_platform/cli.py` 第 54–70 行只有分步命令；`hydro-platform/automation/setup/README.md` 明确安装和调度脚本仍待建设；[recovery.md](recovery.md) 描述的是目标恢复流程。

建议先做一次完整 run-once：读库→对账任务→准备证据包→处理一个/有限个就绪任务→汇总新增/完成/阻塞。缺 PDF 继续等待；完成项跳过；单篇失败不抹掉其他成功项。先验证可补跑、幂等及崩溃恢复，再用计划任务定时调用它。不要直接把各个现有命令按时间串成无状态脚本。

安装脚本需要验证 Python/pypdf、Poppler、Codex CLI 及认证，并在另一套干净环境恢复运行；目前仅配置路径可迁移不等于换机验收完成。Git 同步须用户另行授权，目前不要自动推送。

### P1 / Fast-follow：前置门禁仍依赖 Zotero 索引

`hydro-platform/automation/src/hydro_platform/pdf_gate.py` 第 213–222 行调用附件 fulltext，索引未就绪就进入 WAITING。实际制卡已使用原文件和本机 pypdf。因而即使原 PDF 可读取，也可能仅因 Zotero 索引滞后被卡住；该判断不能证明整篇 PDF 文字完整。

建议门禁用实际原 PDF 的本机可读性作为依据，保留文件身份、大小、页数、可提取性检查；Zotero 索引只作辅助，不再是唯一通行条件。继续不做 OCR，不放行只有摘要或损坏文件。本项没有修改，当前仍按原门禁运行。

### P1 / Fast-follow：主文与补充材料未区分

`hydro-platform/automation/src/hydro_platform/pdf_gate.py` 第 144–150 行对任意多个 PDF 返回 MULTIPLE_PDFS。主文加 Supplement PDF 也会触发，之后卡片可能只能说补充材料未取得。

建议建立可追溯的主附件绑定及补充附件列表；可先利用明确附件标记/名称/元数据做候选选择，歧义保持技术阻塞，不悄悄选第一个。是否将补充材料纳入本轮阅读需要确认，因为会改变读取量与范围。无需为每篇设置人工科研核验。

### P2 / Track：全量重复检查、上下文与本地草稿开销

`hydro-platform/automation/src/hydro_platform/tasks.py` 第 448–458 行在锁内获取全库并对所有父条目运行门禁；`hydro-platform/automation/src/hydro_platform/card_generation.py` 第 335 行将全部启用模板拼入同次请求。库变大后，已完成论文的重复哈希/索引读取和模板上下文会增加成本，但本次没有性能实测，不能报具体降幅。

建议先记录各阶段耗时，再按输入版本复用无变化项，保留定期全量对账；等待 PDF 的旧条目必须继续检查，不能只消费 ITEM_ADDED。当前单会话可复用已提取文字和图像，暂不另造共享全文数据库。

本地 generation-drafts 保住输出后会积累，且不能自动接续校验；后续增加按任务/输入/协议绑定的恢复入口与保留策略，绝不能直接把未校验草稿升级为正式证据。

## Paper Tigers：不值得继续投入的过度担忧

- “只有六个 Agent 才能保证高质量”：数量不是质量证明，当前已出现 49:43 后末阶段失败。应衡量可用结果与失败成本，不恢复固定六角色作为默认。
- “一定要有学生证据卡目录才能看贡献”：共享证据包与成员事件可以分开，重建个人卡库只会增加重复副本。当前成员映射和事件还未实现，不要把目录说明当成监控功能。
- “先建设向量数据库/知识图谱才能生成主题”：现阶段没有证据表明文件结构是首要瓶颈。先用少量真实包验证主题输入输出，再决定索引结构。

## Elephants：重要但尚未验证的假设

1. 详细粗卡能否改善主题结果？现在主题目录只有边界说明，没有实现或验收样例。卡片长、字段多不等于主题好。下一阶段建议用少量既有论文建立主题样例，检查是否能回答“相关论文有哪些、各研究做到了什么、哪些差异只是尺度/口径不同”，由最终主题效果判断输入是否够用，不引入逐卡人工审核。
2. 不独立核实卡片语义时，错误会否在聚合中放大？当前只自动检查来源身份、标记、引用编号和结构；模型仍可能误读图表或将错误解释写在正确标记后。这是残留风险，不应伪称已写死在代码里解决。主题层须保留来源性质和信息边界，不能把 AI 推理当成新增实证。
3. 主卡和定向精读如何更新而不破坏引用？保持主卡/主题精读分离、主题引用证据版本是合理方向，但目前尚未实现精读版本管理，不能承诺自动更新后的引用永远有效。
4. 私人 Zotero 账号能否准确归因每次新增/补 PDF？当前 snapshot 记录 Key、版本、类型、标题、修改时间等，并没有关键贡献事件的创作者映射。应先验证接口真实可提供的字段，未知就记未知，不猜贡献人。该能力按用户要求后置。
