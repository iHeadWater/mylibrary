# 科研工作流

本文面向实际阅读文献和形成研究认识的人，说明自动粗卡、科研证据卡、候选主题、正式主题和idea之间的关系。平台安装和自动化操作不在这里重复，参见[文档入口](index.md)。

## 五类科研对象

| 对象 | 解决的问题 | 当前情况 |
| --- | --- | --- |
| 来源 | 我们实际读的是哪一份文献或数据产品 | Zotero与来源版本规则已有 |
| 自动粗卡 | 快速说明一篇来源研究了什么，便于后续发现 | 自动管线已实现 |
| 科研证据卡 | 哪些Claim经过原文定位，可以支持什么结论 | Skill与模板已有，未自动接入粗卡升级 |
| 主题 | 多个Claim围绕什么稳定研究问题形成综合 | 候选池已实现；正式主题仍需人工闭环 |
| idea候选 | 哪个缺口可以转为可检验研究问题 | 目标设计，尚未实现 |

## 从文献到证据卡

一项来源只登记一次准确版本。Zotero元数据用于识别来源，原始PDF用于核对科学内容。自动管线根据来源类型从九类模板中选择一种，生成详细粗卡并记录PDF指纹、模型、提示词和运行结果。

自动粗卡主要服务于筛选和候选主题发现。它通过的是来源、流程和保存检查，不等于每个数字、因果解释和图表含义都已由人核验。

当某条认识要进入正式主题或科研决策时，使用`skills/hydrology-evidence-cards/`工作流打开原文，把承重内容拆成可定位Claim，并记录推断类型、适用边界、证据来源和人工复核情况。只有达到L2/L3且完成来源核对的Claim，才可以支撑正式主题结论。

## 从证据卡到主题

候选主题用于发现可能的研究问题，允许重叠、不稳定、改名、合并、拆分或被拒绝。自动化可以根据全池粗卡、已有候选和适用精读更新候选主题，但不能把候选直接变成正式主题。

人工筛选至少需要回答：

- 它是不是一个可持续研究的问题，而不只是方法名、地区名或关键词？
- 纳入和排除边界能否说明？
- 哪些来源代表该主题，哪些来源只是相邻或歧义材料？
- 它与已有主题是父子、相邻、重叠、合并还是拆分关系？
- 当前证据是否足以建立，还是应该观察、补证据或拒绝？

人工决定可以是建立、改名后建立、合并、拆分后重审、观察、补证据后再决定或拒绝。只有建立、改名后建立和合并可以产生正式主题，并且必须记录决定人、时间、理由和来源候选。

## 正式主题怎样形成

正式主题至少包含核心研究问题、层级与边界、证据来源、Claim准入、比较框架、当前综合、研究脉络、异质性与争议、迁移边界、证据缺口和后续补证据任务。一级主题表示长期方向，二级主题表示相对稳定的问题群，三级主题只在材料规模和问题边界确有需要时建立。

卡片与主题之间的关系独立保存。新增文献主要增加或更新关系、补充主题综合，不因为主题变化而反复重写证据卡。主题合并、拆分、改名或归档保留历史身份和前后关系，不能直接覆盖旧主题。

主题发现证据不足时，可以产生三类反馈：重新核对某个来源、补充缺失语料、修正发现模型。反馈必须指向受影响的卡片、Claim或发现阶段，说明最小补查材料和停止条件；完成后再重算受影响的主题部分。

## 从主题到idea

idea候选只能从正式主题、已核验Claim和明确缺口中形成。每个候选需要说明研究问题或假设、证据基础、缺口为何存在、研究对象、可用数据、拟用方法、可证伪结果、可行性、潜在贡献、不确定性和风险。

时效、标准化引用、期刊位置和主题增长可以帮助决定先评估哪个idea，但不能提高证据质量，也不能把当前语料中的空白自动宣称为创新。idea是否成立由研究者和导师判断。

## Codex与Obsidian的分工

Codex负责接受自然语言任务、搜索材料、组织证据、生成候选和提出需要人判断的问题。Obsidian负责让研究者阅读卡片、沿链接浏览主题、比较修改和完成审核。

正式接入尚未实现。目标方案以文件型MCP作为Vault的后台接口，第一阶段只读；Obsidian官方CLI负责打开结果和查看差异；Local REST API只在需要当前活动笔记时使用。后续受控写入仅允许指定草稿或协作目录，并要求冲突检测，默认禁止删除、移动和批量改名。

## 完成边界

这条科研工作流完成的判据不是“生成了若干Markdown”，而是：来源可追溯；自动粗卡与已核验证据卡可以区分；候选主题不能绕过人工门；正式主题能够回链Claim并保留演化历史；Obsidian修改不会被后台覆盖；idea候选能够说明证据基础、可检验性和不确定性。
