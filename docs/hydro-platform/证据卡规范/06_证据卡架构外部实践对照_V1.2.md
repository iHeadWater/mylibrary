# 证据卡架构外部实践对照 V1.2

## 1. 对照目的

本文件回答：水利科研平台为什么采用 Source—Claim—Decision 三层、版本化来源、声明定位、条件方法模块和 AI 溯源，而不是继续扩充八份静态长表。

对照结果只提供设计依据。外部标准没有替本项目决定工作流，本平台也不宣称完整实现这些标准。

## 2. 外部事实

### 2.1 W3C PROV-O

[PROV-O](https://www.w3.org/TR/prov-o/) 是 W3C Recommendation，提供 Entity、Activity、Agent 及其关系来交换跨系统来源信息。它支持区分“被读取的来源版本”“提取或校验活动”“执行提取和复核的人或软件”。

### 2.2 W3C Web Annotation Data Model

[Web Annotation Data Model](https://www.w3.org/TR/annotation-model/) 把 Annotation 的 Body 与 Target 分开，并通过 selector／state 等机制定位目标资源中的片段。它支持把一条声明与具体页、节、图表、条款、记录或代码位置连接，而不是只链接整份文献。

### 2.3 DataCite Metadata Schema

[DataCite Metadata Schema](https://schema.datacite.org/) 以一致识别和引用研究资源为目标，包含 Identifier、Version、ResourceType、RelatedIdentifier 等属性。它支持区分作品、具体版本以及与其他资源的关系。

### 2.4 RO-Crate

[RO-Crate 规范](https://www.researchobject.org/ro-crate/specification.html) 使用 JSON-LD 图描述研究对象中的文件、数据、人员、软件、工作流和上下文实体，并用稳定标识互相引用。它支持“Markdown 作为可读入口、结构化图作为派生视图”的组合。

### 2.5 FAIR 原则

[FAIR Principles](https://www.go-fair.org/fair-principles/) 要求数字研究对象可发现、可访问、可互操作和可复用，并强调持久标识、丰富元数据、关系和来源信息。FAIR 不等于开放，也不证明科研质量。

### 2.6 科研报告和证据综合指南

- [Cochrane Handbook Chapter 5](https://training.cochrane.org/handbook/current/chapter-05) 强调预先定义问题、结局、研究特征和数据提取过程。
- [PRISMA 2020](https://www.prisma-statement.org/prisma-2020) 要求系统综述报告检索、筛选、纳入、偏倚和综合过程。
- [STROBE](https://www.strobe-statement.org/) 覆盖观察性研究报告所需的设计、对象、变量、偏倚和统计信息。
- [TRIPOD+AI](https://www.tripod-statement.org/) 面向临床预测模型报告；本平台只借鉴其“数据、模型、验证和使用场景分开”的通用原则，不把临床清单直接当作水文模型质量标准。
- [USGS Data Management](https://www.usgs.gov/data-management) 强调数据生命周期、元数据、质量、保存和发布责任。

报告清单可以暴露缺失报告，不能独立证明方法学质量或结论正确。

## 3. 可借鉴原则

| 外部实践 | 可借鉴原则 | 在本平台中的接口 |
| --- | --- | --- |
| PROV-O | 实体、活动和责任主体分开 | 来源版本、提取方法、生成器版本、人审状态和复核人分别记录 |
| Web Annotation | 声明与精确目标片段分开 | claim-json 的 locator 指向页、节、图表、条款、记录或代码位置 |
| DataCite | 标识、版本、类型和关联关系分开 | source_work_id、source_manifestation_id、source_version、artifact_type、version_family_ids |
| RO-Crate | 研究对象形成可引用关系图 | Source、Claim、Decision 节点和关系边；由脚本导出派生 JSON 图 |
| FAIR | 标识、元数据、来源和可复用边界 | 稳定 ID、来源入口、版本快照、访问级别、许可和 recheck_trigger |
| Cochrane／PRISMA | 综合过程可审计并防重复计数 | 综述来源卡与平台决策卡分开；记录检索、纳入、重叠和独立性组 |
| STROBE／TRIPOD+AI | 研究设计、样本和验证信息透明 | 原创研究公共字段加条件方法模块，不用一份清单覆盖所有方法 |
| USGS 数据管理 | 数据版本、质量和生命周期可追踪 | 数据快照、manifest、质量标记、修订链、抽检和适用性分别记录 |

## 4. Codex 推断

1. 水利来源类型多，但跨来源共享“身份、版本、来源、声明、定位、边界、核查和决策关系”。因此公共骨架应该只维护一次。
2. 来源类型决定证据怎样产生，推断／方法类型决定必须检查哪些假设，水利情境决定结论能否迁移。三者应正交组合。
3. 同一来源可服务多个问题，完整复制来源卡会造成版本和核查漂移。声明需要全局 ID，决策需要只引用声明 ID。
4. Markdown 适合人工阅读和 Git 审阅；嵌入严格 JSON 块可在不引入数据库或 YAML 扩展依赖的情况下完成硬校验和关系图导出。
5. 自动检查适合阻断明显的结构越界，不适合给跨来源科学质量打统一总分。

以上是结合外部原则形成的设计推断，不是外部标准原文结论。

## 5. 本项目选择

1. 一个具体来源版本只维护一张正式来源卡；source_work_id 连接同一作品的不同版本。
2. 保留八个独立来源类型入口，但每个入口只维护该类型的证据生成机制。公共骨架、L0—L3、Cxx、water_context 和方法模块由 Skill 装配。
3. 用 claim-json 保存原子声明，用 decision-json 保存平台证据综合，用 water-context-json 保存水利情境。
4. 只有 L2、L3 声明可进入平台决策卡；L3 仍受动态精读三门判定约束。
5. 相关性、核查准备度、适用性和决策作用分成四个字段；决策卡另设六维证据画像，不设置总分。
6. 对 AI 提取实施 R08 来源快照、人审和声明级核查；AI 置信度不得代替科学确定性。
7. 对未解决承重冲突实施 R07 阻断，不允许 approved、verified 或 direct。
8. Git 中保存卡片、规则、清单和派生关系图；全文、原始数据、Zotero 数据库、凭据和受限工程资料留在授权系统。

## 6. 未采用或暂不实现

- 不实现完整 PROV-O、RO-Crate 或 Web Annotation 服务端；当前只保留可映射字段和稳定关系。
- 不把报告清单转成科研质量得分。
- 不用同一量表直接比较标准条款、工程运行记录、统计估计和软件运行。
- 不因来源官方、开放、可下载、可安装或自动校验 PASS 而升级科学结论。
