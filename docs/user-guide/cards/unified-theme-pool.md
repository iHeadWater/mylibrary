# 统一文献池与主题池

**一个研究问题 = 一个长期主题。** 文献增加时，已有主题持续演化，而不是每批新文献各生成一套主题。

**要解决的问题**：老师和学生需要看到同一个研究问题随文献积累而持续演化，不必在多个批次之间自己对照。
已确认的做法是：候选主题可以**自动**补充、修正、合并、拆分；**正式主题不自动覆盖**；
人**不**逐卡、逐次审批。

- 文献仍是**一篇一个证据包**，PDF 由 Zotero 管理。
- 主题发现的输入 = 当前群组**全部可用粗卡** + 已有主题的**修订正文** + **来源版本仍匹配**的历史精读。
  输入指纹变化只提示「有新输入」，**不限制跨批次关联**。
- 当前针对**小样本**文献库：这些材料一次送进一个规划上下文。**大规模上下文的检索/压缩尚未实现**，
  不能宣称任意规模都适用。

## 四条行为约定

### 一、已有主题持续更新

设计与实现：`hydrolitagent/cards/theme_pool_runner.py`、`hydrolitagent/cards/assets/templates/themes/pool-discovery.md`。

1. 补充、修正、改名用 **UPDATE**，**沿用 `theme_id`**、保存新版本，**不覆盖**旧版本。
2. 规划同时取得**统一文献池**和已有修订主题 —— 不以新增日期或批次为输入边界。
3. 不需要变更时 `actions` 可以为空；但仍记录「本次输入已处理」，**无变化下次不调用模型**。
4. 科学关联的依据由模板指导；**程序不按关键词强行合并**，也不校验正文标题、篇幅或标签。

### 二、候选自动合并与拆分

设计：`hydrolitagent/cards/theme_pool.py`。

1. **MERGE** 至少两个当前候选产生一个**新编号**；**SPLIT** 一个当前候选产生至少两个新编号。
2. 所有新版本所需的精读与回填**全部保存后**，才一次更新注册表；任一失败时旧主题仍有效。
3. 父主题转 `SUPERSEDED` 但**不删除**；父/子**双向**记录编号关系，旧正文与引用保留。
4. 未被操作的主题保持原样；同一主题本轮**不得**被互相矛盾地操作多次。
5. 正式主题、已被替代的历史主题**不能**作为修改对象；对正式主题的建议只能**另建候选**，在正文里引用其编号。

### 三、精读按适用性复用

设计：`hydrolitagent/cards/theme_pool.py`。

1. Agent 根据原 focus、上下文与精读正文选择 `reuse_reading_id` 并说明适用理由；
   **不会**仅凭「论文相同」强制复用。
2. Python 检查引用确实存在、原始来源与当前证据包一致、文件未变；
   **不能**引用另一篇或旧来源版本冒充。
3. 重点变化或旧精读不足时，从当前原始 PDF **再次定向阅读**并保存新精读；**不改**粗卡或旧精读。
4. 复用引用进入新版本的回填输入，保留其原重点与当前用途；精读记录**独立于运行批次**。
5. 适用性判断仍是 **AI 判断**，不是程序已独立证明科学正确；不增加第二个复核 Agent。

### 四、安全迁移与中断恢复

设计：`hydrolitagent/cards/theme_pool.py`。

1. 全部**已完成**的旧批次接入**同一个**注册表；同名问题不会仅因标题相同就被程序强行合并。
2. 原主题编号、旧文件与精读引用保留。只有**一个**与当前输入完全匹配的旧完成批次时，
   可直接接入并**跳过**新模型调用。
3. 多个历史批次要**一起**交给后续规划，而不是随意选最新一个；`migrate-only` **始终不调用模型**。
4. 模型结果先落盘，失败后复用已完成步骤；**注册表是本次变更对外生效的提交点**。
5. 注册表指针写入中断或缺失时，只从**完整、无分叉**的历史提交链恢复；链不全、人工改动、来源冲突
   → **停止**，不删除也不覆盖。
6. 本地运行目录丢失**不影响**共享注册表、版本与精读复用；
   这些共享成果必须**实际备份** —— 不能从未推送的 Git 版本凭空恢复。

## 怎么运行

在**仓库根**执行：

```bash
uv run hydrolitagent cards themes-run --json
```

只读预览 / 仅迁移旧成果：

```bash
uv run hydrolitagent cards themes-run --dry-run --json
uv run hydrolitagent cards themes-run --migrate-only --json
```

主要阅读入口是 `themes/index.md`。进入某个主题后主要看精读回填的 `revised.md`，
不必从文件夹猜最新版。**不要手改**程序维护的索引或注册表 —— 自由编辑这些生成文件会作为
「保留人工修改」的冲突报告，而不是被自动覆盖。

## 存储分工

| 位置 | 作用 |
|---|---|
| `themes/index.md` | 当前候选、历史主题与版本链接；给人看的总入口 |
| `themes/_registry.json` | 稳定编号、当前版本、历史版本、前身/后继、输入处理指纹 |
| `themes/candidates/TH-编号/versions/CHANGE-编号/` | 新主题及更新版本；`initial.md` 初版、`revised.md` 回填结果、plan/manifest/结果 JSON |
| `themes/changes/CHANGE-编号/` | 一次处理的输入、规划、结果发布记录；**不是**独立知识池，也不是 Git commit |
| `themes/changes/IMPORT-编号/` | 已有成果接入统一池的记录 |
| `themes/candidates/BATCH-*/` | 已有旧成果的**原位置**，继续被统一池引用，不搬动、不重做 |
| `themes/confirmed/` | 正式主题预留区；专用人工确认入口**尚未实现** |

目录长这样：

```text
themes/
  index.md                       当前候选、历史主题与版本链接
  _registry.json                 稳定身份、当前版本、历史版本、合并/拆分关系
  candidates/TH-编号/versions/CHANGE-编号/
    initial.md / revised.md      本次初版与精读回填结果
    plan.json / manifest.json    变更类型、理由、父主题与来源引用
    revision-result.json         已保存模型结果，可恢复中断
  changes/CHANGE-编号/            输入、规划结果、执行计划、完整提交记录
  changes/IMPORT-编号/            旧成果接入记录
  candidates/BATCH-*/            旧成果的原始存放位置，保留链接兼容
evidence-packs/EV-*/readings/RD-*/  独立保存的精读结果
```

### 演化规则速查

- 补充 / 修正：沿用主题编号，**增加版本**。
- 合并 / 拆分：**创建新编号**，旧主题保留为历史，前后**双向追溯**。
- 精读：适用时**复用**；问题/重点改变且旧精读不足时，**再读原始 PDF**。
- 定向精读始终存在对应证据包的 `readings/` 里，**主题只引用**，不改主粗卡。
- 所有新版本**准备完才整体发布**；失败时不先废弃旧主题，已完成步骤可续用。
- 正式主题**不能被自动操作覆盖**；更新建议**另建候选**。
- 相同输入**不调用模型**；换批次**不构成**重读理由。

新主题**不放入** BATCH 目录。已迁移主题第一次更新时，在其稳定编号下保存新版本；旧版本仍留原位置。
运行记录里的 CHANGE **只描述一次处理**，不拥有主题。未完成的旧批次**不会**被自动当作已完成主题导入，
原文件仍保留。

## 候选主题

候选主题用于组织研究问题与证据，**不是**已经人工确认的正式结论。自动补充、修正、合并、拆分
**不逐次**要求人工审批。

新建 / 更新结果采用 `TH-稳定编号/versions/CHANGE-处理编号/`：

- `initial.md`：依据粗卡规划的本次候选初版。
- `revised.md`：完成必要精读或复用已有精读后，回填修订的候选；**日常主要看它**。
- `plan.json`：变更类型、原因、来源主题及精读安排。
- `manifest.json`：版本状态、来源和实际精读引用。
- `revision-result.json`：回填输入、模型结果与执行记录，支持续跑。

**新结果准备完后才更新全池注册表**；目录里出现半成品不代表它已成为当前主题。
请从 `themes/index.md` 查当前版本；不要手改索引/注册表或移动被引用的文件 ——
冲突时程序**保留文件**而非覆盖。

旧 BATCH 目录原样保留，并已接入统一池。旧主题下次更新沿用编号、在新目录追加版本，**不改旧链接**。
精读仍存于对应论文的证据包，**不复制** PDF 或主粗卡。

当前已有两个迁移后的候选，**均未**人工转正式。合并/拆分的程序保护有测试，
**真实 AI 关联判断质量仍待实测**。

## 正式主题预留区

产品规则：候选必须完成定向精读与回填，**并由人确认**，才能成为正式主题。

专用确认命令/界面**尚未开发** —— `themes/confirmed/` 里只有说明文件，不代表已经有正式主题。
普通 `themes-run` **不自动晋级**，也不向这里写入候选。

统一池的操作检查会保护已标记为正式的主题：**不能**被自动 UPDATE / MERGE / SPLIT；
系统可以另建候选建议并引用其编号。不要靠随手移动文件或手改注册表来「模拟确认」——
这会破坏追溯或触发冲突。

路径继续由总配置的 `paths.themes_dir`、`evidence_packs_dir`、`logs_dir`、`lock_file` 推导；
模板目录、模型、思考强度和研究目标沿用 `theme_pipeline`。**没有**新增某台电脑的硬编码路径或密钥。
只在指定制卡机运行，沿用单机主题锁。

## 验证与未证明事项

```bash
uv run pytest tests/test_theme_pool.py tests/test_themes.py -q
```

验证稳定 ID、复用/重读、合并/拆分、失败保护、迁移和中断恢复等**程序规则**。
这些测试只能证明路由、数据保护与恢复行为。

**仍未验收**：新文献引发的真实模型合并/拆分质量、人工确认体验、大规模文献下的检索压缩。
不存在机器认证的科学正确性或期刊成果保证。干净异机、关机后登录和云端同步同样属于独立验收项。
